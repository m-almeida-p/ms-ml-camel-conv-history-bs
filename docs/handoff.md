# Handoff: where this stands and how to keep going

Read this first if you are picking the work up (a person or another agent). It says what exists, what state it is in, the rules the
owner set, how to change something safely, and what is still open. Everything else is linked from [README.md](README.md).

## What this is

Three Apache Camel Karavan projects that serve conversation history through the **Microsoft Foundry Conversations API**, with the
same HTTP contract as the Go service `ms-ml-conv-history-bs` (copied unchanged in `docs/contract/`):

| Project | Does |
|---|---|
| `conv-history-consumer` | Kafka topic `yape.public.conversation_events` (Debezium outbox of the agent's event store) into Postgres schema `camel_history` |
| `conv-history-sync` | Copies each chat message into a Foundry conversation, once and in order; keeps the map between our ids and Foundry's |
| `conv-history-api` | `GET /v1/conversations` (from Postgres) and `GET /v1/conversations/{id}/messages` (text and order from Foundry, the rest from Postgres) |

Why a hybrid: Foundry items carry no time and no metadata, ids are generated by Foundry, and conversations cannot be listed by
account. So Postgres stays as the index and holds everything Foundry drops. See [design-foundry.md](design-foundry.md).

## Is it healthy? (one minute)

```bash
docker ps --format '{{.Names}} {{.Status}}' | grep -E 'conv-history|foundry-token|fake-foundry'   # three projects and the broker healthy
curl -s localhost:8086/health                                  # {"status":"ok"}
./scripts/oracle-api.sh | tail -2                              # the API returns exactly what the data says
./scripts/check-foundry-sync.sh | tail -2                      # Foundry holds exactly what camel_history says, 0 orphans
docker exec yape-kafka kafka-consumer-groups --bootstrap-server kafka:29092 --describe --group ms-ml-camel-conv-history-sync | awk '$6 ~ /^[0-9]+$/ {l+=$6} END {print "lag", l+0}'
```

Needs the shared cluster up (`../cluster/scripts/up.sh`, network `yape-local`) and Karavan (`./scripts/up.sh`, UI on
`http://localhost:9998`, bound to `127.0.0.1`). Start-up from nothing: [karavan-setup.md](karavan-setup.md) and
[foundry-setup.md](foundry-setup.md).

## The rules the owner set

These stand until the owner changes them.

- **Never run the Go service** (`ms-ml-conv-history-bs`) or its consumer. The oracle (`scripts/oracle-api.sh`) replaces parity with it.
- **Never commit in `../ml-genai-agents-bs-testing`.** It is the producer repo and holds the owner's uncommitted migrations
  `000001` to `000004`, a README and `scripts/check-migrations.sh`. A **new table goes through a migration there**, not through SQL here.
- **Never run that repo's `run.sh --clean`.** **Never reset or delete the consumer group `ms-ml-conv-history-bs`** (the original
  service's). Ours are `ms-ml-camel-conv-history-bs` (consumer) and `ms-ml-camel-conv-history-sync`; resetting those is allowed only
  on purpose, with the project stopped.
- **Secrets only in `.env`** (git-ignored). Never in chat, in a file, in a log or in a command line you paste. Never run `bash -x` on a
  script that reads `.env`: it prints the values. **Run `./scripts/scan-secrets.sh` before every push**; it looks for the real values
  and prints only counts.
- **Fake data only.** Delete every Foundry conversation a test creates (the suites do; `foundry-limits-probe.py --cleanup-only` and
  `foundry-cleanup-orphans.sh` repair an interrupted run).
- **The owner does the Azure and Karavan logins.** Do not try to log in for them.
- **One Foundry item per call.** Batches of 20 are deferred to V2.
- Commits are free (one per task). Pushing is authorized, because Karavan reads the repository from GitHub; scan first.
- Phase documents in `temp/` are Spanish; everything in `docs/` is English.

## Changing something safely

1. **Test first.** For a bug, write the failing test, see it fail, then fix ([testing.md](testing.md#adding-a-test)).
2. `./scripts/test-camel.sh <module>` while you work, then `./scripts/test-all.sh` before you finish.
3. `python3 -I scripts/check-docs.py` if you touched a route, a step label or a doc. It checks that every `Docs:` pointer in a
   Designer note resolves, every link works, every label fits the Designer, and every diagram renders.
4. Commit, `./scripts/scan-secrets.sh`, push.
5. **Deploy to Karavan, one project at a time**, and confirm each is healthy before the next:
   in the UI open the project, **Source**, **Pull**, confirm; then `docker rm -f <project>`; reload the page; press the **top-right
   Run** (not the one in the Containers tab); wait for `healthy`. Order: consumer, sync, API. Then run the oracle and
   `check-foundry-sync.sh`. A changed `application.properties` or `docker-compose.yaml` needs the container recreated, not restarted.
6. If you changed a step label, open the route in the Designer: it draws 32 characters and cuts the rest ([troubleshooting.md](troubleshooting.md)).

Faster loop without Karavan: `./scripts/devmode-local.sh <project> [NAME=value]` runs a project in the same DevMode image on a
throwaway topic. The tests use it.

Things that cost time before ([troubleshooting.md](troubleshooting.md) has each with its fix): a stray file in a project folder
crashes its container (Run copies every file); Karavan's compose parser reads ports as `host:container` and fails on
`127.0.0.1:8086:8080`, so a project's ports cannot be bound to the loopback; macOS `/private/tmp` is invisible to Docker (use `$HOME`
or `.devmode-local/`); `docker exec -i` swallows a script's stdin; BSD `sed -i` needs a suffix; a Camel `onException` inherits the Dead
Letter Channel's exponential back-off unless you switch it off; project exception classes cannot be named in YAML, so they extend
built-in ones.

## Scripts that can hurt

| Script | Why |
|---|---|
| `scripts/parity-check.sh` | Empties `camel_history`'s three tables. Refuses unless `--wipe-camel-history` |
| `scripts/clean.sh` | Removes Karavan's containers **and its database volume** (the projects are safe: they are in Git) |
| `scripts/foundry-cleanup-orphans.sh --delete` | Deletes Foundry conversations. Scoped to our `source` and `--instance`, and refuses with an empty map |
| `docker rm -f conv-history-*` | Normal when redeploying, but the project is down until you press Run again |
| `scripts/foundry-limits-probe.py` | Creates up to hundreds of conversations on the real project (all deleted at the end) |

## Not ready for production

It is a local PoC and says so. Known, accepted by the owner:

- **No authentication.** `/messages` takes no account, so anyone who knows a conversation id reads it ([conv-history-api.md](conv-history-api.md#who-can-call-it)).
  A gateway must bind `idYapeAccount` to the caller.
- **Chat text and the account id are written to the dead-letter log** (and so to container logs). Accepted for the PoC. The offset is
  enough to replay; log only reason, field, topic, partition and offset if this goes further.
- **The token broker hands a Foundry User token to any container on `yape-local`.** Accepted; isolate it on its own network if the
  network is shared. The three services use the `postgres` superuser with no password (the cluster's convention).
- **The three services' ports (8086, 8084, 8081) are on all interfaces.** Karavan and its registry are on `127.0.0.1`. See the
  limitation above; the options are a host firewall or a gateway.
- The Camel management port (9876) has `sendEnabled`, `downloadEnabled` and the dev console on. It answers only health today
  (checked), but turn them off before sharing the network.

## Decisions that shaped the design

| Decision | Why | Detail |
|---|---|---|
| Postgres keeps time, role, author, sequence and metadata; Foundry keeps text and order | Foundry items have no `created_at` (null, measured) and drop metadata. The Responses API's `created_at` is per response and exists only for model calls; none are made here, so `GET /openai/v1/responses?conversation_id=` returns nothing for our conversations | [design-foundry.md](design-foundry.md) |
| One item per Foundry call; check, then send, in one step | Foundry has **no idempotency key** (the header is ignored). A call whose answer is lost may have been kept, so every retry looks first | [conv-history-sync.md](conv-history-sync.md#reconciliation) |
| Earlier stored messages that Foundry lacks are sent before the current one | A skipped record must not become a permanent gap; if Foundry already holds a later one, rebuild | same |
| Rebuild creates and maps the new conversation, then deletes the old | A refusal or crash must never leave the conversation without a copy | [conv-history-sync.md](conv-history-sync.md#rebuilding-a-conversation) |
| A token broker, not a secret in a project | Karavan-run containers get no environment and project files go to Git | [foundry-setup.md](foundry-setup.md) |
| Dependency down is a 503, not a 500 | The contract lists 500 only; `contract-check.py` allows 503 for this one case | [conv-history-api.md](conv-history-api.md) |
| Two copies of `ConversationEventDecoder`, `OffsetCommit`, `PoisonRecordException`, `StoreRefusal` | Karavan projects cannot share a class. A test and `test-sync.sh base` keep them identical | [testing.md](testing.md) |
| Foundry's conversation metadata: `conversation_id`, `source`, `instance` | Orphans are found by listing and filtering (Foundry cannot filter by metadata); `instance` keeps two stacks on one project apart | [conv-history-sync.md](conv-history-sync.md) |
